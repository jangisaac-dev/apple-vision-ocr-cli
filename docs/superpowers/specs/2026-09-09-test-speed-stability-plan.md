# 자동화 테스트 / 속도 / 안정성 개선 계획

작성: 2026-09-09
베이스라인(이 세션 실측): `swift test` → 91 tests, 0 failures, **0.243s**

## 진단

**핵심 사실 하나:** 전체 테스트 스위트가 0.243초에 끝난다. 즉 91개 전부
파싱·계획·기하 계산 유닛 테스트이고, **프로세스를 띄우는 코드 경로에는
자동 테스트가 하나도 없다.** 이 프로젝트의 성능은 전적으로 멀티프로세스
split 경로에서 나오는데, 정확히 그 경로가 무검증이다.

| 영역 | 현재 | 갭 |
|---|---|---|
| CI | 없음 | 91 테스트가 사람이 기억할 때만 돌아감 |
| split `run()` | 유닛 4개(planChunks/merge/writeCombinedText) | 프로세스 스폰·진행률 파싱·워커 실패·취소·일시정지 = 전부 `VOCR_HEADLESS` 수동 |
| single↔split 동등성 | 라운드마다 손으로 SHA-256 비교 | 자동 회귀 테스트 없음. PDF는 "추출 문자 수 일치"만 확인 → 내용 동등성 미보장 |
| 벤치마크 | CURRENT_STATUS.md에 손으로 붙여넣은 숫자 | 스크립트 없음 → 회귀 감지 불가 |

## Phase 0 — 측정 하네스 (선행 조건)

다른 모든 판단의 근거. **이것 없이 Phase 3을 시작하지 않는다.**

**먼저: 커밋된 다중 페이지 픽스처가 없다.** `Samples/`에는 1페이지 PDF뿐이고,
지금까지의 모든 벤치마크는 커밋된 적 없는 `.build/bench/` 산출물에 의존했다.
그 디렉터리는 이미 삭제되어 과거 숫자를 아무도 재현할 수 없다. 밀집
한/영 다중 페이지 PDF를 **생성 스크립트째** 저장소에 넣는 것이 Phase 0의 첫 항목이다.

- `SplitProcessOCRRunner`가 워커별 종료 시각을 stderr 한 줄로 남긴다
  (`[split] worker N pages A-B done in Xs`).
- `scripts/bench.sh`: 고정 픽스처에 single / split N을 3회 돌려 wall time
  중앙값, 워커 종료 시각 spread, 부모+자식 합산 최대 RSS를 출력.

**검증:** 워커 12개 종료 시각 spread가 찍힌다.
**주의:** RSS는 반드시 100p 이상 픽스처로 측정한다. split에서 워커당 페이지는
`pageCount/N`이므로 24p·12워커면 워커당 2페이지 — 렌더 큐(기본 32)가 아예
채워지지 않아 메모리 문제가 보이지 않는다.
**판정:** spread가 크면 straggler 가설 성립 → Phase 3c 진행.
작으면 **동적 분할 계획을 폐기한다.** (현재 straggler는 추정일 뿐 미측정)

## Phase 1 — 자동화 테스트 (최우선)

1. **CI.** `.github/workflows/ci.yml`, macOS runner, `swift build -c release`
   + `swift test`. 약 10줄.
   **검증:** 푸시에서 초록.
2. **`run()` 통합 테스트.** `executableURL`이 주입 가능하다는 점을 이용해
   가짜 워커 스크립트를 자식으로 띄운다: 비정상 종료(exit 1) → 에러 전파와
   stderr tail 포함, 멈춘 자식 → 제한 시간 내 반환, 일시정지 중 취소 →
   SIGCONT 후 종료. 실제 Vision 불필요 → CI에서 빠르고 안전.
   **부모→자식 인자 계약도 함께 검사한다.** 가짜 워커가 받은 `$@`를 파일로
   덤프하고 `--page-range A-B`, `--txt-only`/`--output`, 요청 시 `--page-breaks`가
   실제로 넘어갔는지 단언한다. 이 저장소가 이미 한 번 낸 회귀(b8856d6: GUI split에
   `--page-breaks`가 전달되지 않아 페이지 구분자가 사라짐)가 바로 이 계층이고,
   exit 1 / hang만 보는 가짜 워커로는 절대 못 잡는다.
   **검증:** 각 케이스가 제한 시간 내 반환하고, 스폰한 자식 PID가 전부 사라지고,
   실패 시 산출물과 임시 디렉터리가 남지 않는다.
3. **동등성 골든 테스트.** 작은 한/영 픽스처 PDF(빈 페이지·불균등 분할·회전·
   기존 텍스트 레이어 포함)로 single vs split을 비교. TXT는 `cmp`, PDF는
   **페이지별** 추출 문자열과 순서를 비교(문자 수 합계로 갈음하지 않는다).
   실제 Vision이 필요하므로 CI 밖 별도 스크립트.
   **검증:** 바이트/페이지별 일치.

## Phase 2 — 종료 안정성

우선순위 주의: **2.1/2.2는 결함이 아니라 값싼 보험이다.** `Sources/`에
시그널 핸들러가 하나도 없음을 확인했고(`grep signal|sigaction|SIGTERM` →
`NSCondition.signal()`뿐), 기본 disposition에서 자식은 SIGTERM을 무시할 수 없다.
2026-06-13 취소 E2E도 워커 12개가 ~0.7초 내 전부 종료됐다. 실제로 물린 적 없는
경로다. 2.3/2.4가 진짜 항목이다.

1. (보험) `terminate()` 뒤 `waitUntilExit()`에 제한 시간이 없다
   (`SplitProcessOCRRunner.swift:258` 부근). → 유예 2초 후 남은 것만 SIGKILL.
2. (보험) `readerGroup.wait()`도 무제한 → `wait(timeout:)`.
3. `writeCombinedText`에 출력 존재 가드가 없다(`mergePDFs`에는 있음).
   CLI 검증과 GUI의 `UniqueOutputPathResolver`가 앞에서 막아주므로 지금은
   TOCTOU 창뿐이지만, 대칭이 아니라서 언젠가 남의 파일을 덮는다. 1줄.
4. 부모 SIGKILL 시 자식 고아화. 자식 CLI가 `getppid()`를 감시해 자멸하는 게
   최소 해법(macOS엔 `PDEATHSIG` 없음). **제약:** SIGSTOP된 자식은 자기
   감시도 멈추므로 일시정지 중 부모가 죽으면 여전히 남는다 — 문서화한다.

**검증:** TERM 무시 워커 픽스처로 취소가 제한 시간 내 끝나고 고아 PID 0개.

## Phase 3 — 속도 (Phase 0 측정 이후에만)

1. **split 자식의 렌더 큐 용량을 낮춘다 (메모리).** 워커 하나의 동시
   비트맵은 대략 `렌더큐(32) + pp(8)`로 **곱이 아니라 합**이다. 따라서 큰 쪽은
   큐다: 32→4면 워커당 ~28장이 줄고, pp 8→1은 ~7장이 준다.
   - 주 레버: `APPLE_VISION_OCR_QUEUE_CAPACITY` — 이미 존재하는 환경변수
     (`SearchablePDFPipeline.swift:211`). `runChildProcesses`에서 자식
     `process.environment`에 넣기만 하면 된다. **새 CLI 인자 0개.**
   - 부 레버: `--page-parallelism 1`. 현재 `childArguments`가 pp를 전혀 넘기지
     않아 자식이 기본값 8을 쓴다. Vision은 프로세스 내부에서 인식을
     직렬화하므로 pp>1은 throughput에 무효(기존 실측).
   둘 다 Phase 0의 RSS 측정 결과를 보고 결정한다. 측정 없이 건드리지 않는다.
   **검증:** wall time 동일 이하 + 최대 RSS 감소, 100p 이상 픽스처에서.
2. **PDF 워커의 전체 문서 텍스트 스캔 중복 제거.**
   `SearchablePDFPipeline.pagesWithExistingTextIfNeeded`가 `options.pageRange`를
   무시하고 문서 전체를 `PDFTextPresenceDetector.inspect`한다. split PDF에서
   워커 12개가 각각 전체 PDF를 PDFKit으로 열고 전 페이지 텍스트를 추출한다.
   `selectedPageNumbers`로 범위를 제한. 약 3줄.
   **검증:** 스캔 입력(텍스트 레이어 없음)에선 미미하고 텍스트 레이어 있는
   입력에서 이득이 크다 — 두 경우 다 측정해서 숫자로 남긴다.
3. **동적 분할은 조건부.** Phase 0에서 종료 시각 spread가 실제로 크게
   나올 때만: 청크를 워커수×3으로 쪼개고 빈 워커에 다음 청크를 배정
   (병합 순서는 청크 인덱스로 유지). 아니면 하지 않는다.

## 순서

Phase 0 → 1 → 2 → 3. 1과 2는 병렬 가능.
구현은 codex에 위임(codex-first), 이 파일만 들고 새 세션에서 시작.

## 범위 밖으로 남기는 것

- `usesLanguageCorrection = false`: 속도 레버지만 한국어 품질 회귀 위험.
  별도 품질 검증 과제.
- 텍스트 레이어 있는 페이지 OCR 스킵: 출력 의미가 바뀜. 별도 결정 사항.
- 병합 PDF가 ~20% 큰 문제(청크별 폰트 중복): 무해, 방치.
- 복합 TXT+PDF 동시 출력의 병렬화: 현재 in-process 폴백, 별도 과제.

# 실행 결과 (2026-09-09)

## 하네스로 얻은 실측 (120페이지 밀집 래스터 픽스처, M5 Pro 18코어)

베이스라인 (개선 전 바이너리, TXT 출력):

| 워커 | median wall | 피크 RSS | 워커 spread |
|---|---|---|---|
| 1 | 343.75s | 1693.8 MB | — |
| 4 | 103.78s | 2661.3 MB | 6.46s |
| 8 | 65.27s | 3343.6 MB | 4.32s |
| 12 | 53.99s (6.4x) | 4242.6 MB | 6.22s |

## 판정 1 — straggler: 이번 입력에서는 우선순위 낮음 (일반적 기각 아님)

12워커 spread 6.22s / 53.99s = 런타임의 11.5%. 동적 분할이 회수 가능한
상한이 11%인데 계획에서 코드가 가장 많은 항목이다. 8→12 워커 증설로 얻은
이득이 17%뿐인 것과 대조하면 sublinear scaling의 주범은 straggler가 아니다.
**Phase 3c(동적 분할)는 보류한다.**

한정 조건: 픽스처는 모든 페이지에 같은 밀도의 40줄을 넣는 균일 문서다.
페이지별 부하 편차가 큰 실제 문서에서는 spread가 더 클 수 있고, 그건
측정하지 않았다. "이 입력에서 우선순위가 낮다"까지가 근거가 닿는 범위다.

## 판정 2 — 렌더 큐는 메모리 원인이 아니다

12워커 TXT에서 `APPLE_VISION_OCR_QUEUE_CAPACITY`를 스윕:

| 큐 용량 | median wall | 피크 RSS |
|---|---|---|
| 32 (기본) | 49.53s | 4252.8 MB |
| 8 | 51.53s | 4251.0 MB |
| 4 | 48.46s | 4255.3 MB |

RSS가 4251~4255 MB로 평평했다. **그러나 이 실험은 큐 한계를 건드리지 못했다.**
120페이지 ÷ 12워커 = 자식당 10페이지이므로 용량 32짜리 큐는 애초에 채워질 수
없다. 따라서 "큐는 메모리 원인이 아니다"는 이 데이터로 결론지을 수 없다.
아래 판정 2-보강에서 한 프로세스에 120페이지를 모두 넣고 다시 측정했다.

### 판정 2-보강 — 큐가 실제로 바인딩되는 조건에서 재측정

단일 프로세스에 120페이지 전부(자식당 10페이지가 아니라 한 프로세스가 120페이지)
투입해 큐가 확실히 가득 찰 수 있게 만든 뒤:

| 큐 용량 | wall | 피크 RSS |
|---|---|---|
| 32 (기본) | 335.84s | 1682 MB |
| 4 | 356.96s | **1673 MB** |

큐를 8분의 1로 줄여 아낀 메모리가 **9MB(0.5%)**, 대신 wall time은 6% 늘었다.
큐가 완전히 바인딩되는 조건에서도 결론은 유지된다: **렌더 큐는 메모리
드라이버가 아니며, 줄이면 손해다.** (원래 실험은 자식당 10페이지라 큐가
채워질 수 없어 근거가 약했다는 지적은 정당했고, 더 강한 조건에서 다시 확인했다.)

## 판정 3 — 전체 문서 텍스트 스캔 중복 제거는 스캔 입력에서 무효

PDF 출력, 12워커, 개선 전/후 바이너리 직접 비교:

- 개선 전: 55.95s, 53.66s
- 개선 후: 55.50s, 54.31s

차이 없음. 이유는 명확하다 — 픽스처에 텍스트 레이어가 없어 `page.string`이
즉시 nil을 반환하므로 전체 문서를 훑어도 비용이 거의 0이다. 이 최적화는
**텍스트 레이어가 있는 입력에서만** 의미가 있고, 이 도구의 주 사용처인
스캔 문서에서는 이득이 없다. 코드는 남기되(더 정확하므로) 속도 개선으로
계상하지 않는다.

## 판정 4 — 유일하게 실측된 속도 개선: 워커 수 기본값

개선 후 바이너리, TXT, 120페이지:

| 워커 | median wall | 피크 RSS |
|---|---|---|
| 12 (현재 기본) | 49.53s | 4252.8 MB |
| **14** | **46.60s** | 4651.2 MB |
| 16 | 48.05s | 5098.8 MB |

깔끔한 역U자다. 14가 최저이고 16은 과구독으로 다시 느려지면서 메모리만
850MB 더 쓴다.

위 표는 설정별로 3회씩 순차 실행한 값이라 시간대·발열 영향을 배제하지 못한다.
그래서 12와 14를 **교차로** 번갈아 실행해 다시 쟀다:

| 반복 | 12워커 | 14워커 | 차이 |
|---|---|---|---|
| 1 | 45.85s | 43.67s | -4.8% |
| 2 | 45.55s | 43.75s | -4.0% |
| 3 | 49.92s | 47.25s | -5.3% |

**3쌍 모두에서 14가 이긴다.** 3회차에서 양쪽이 함께 느려진 것(발열 드리프트)을
교차 측정이 정확히 흡수했다. 실제 이득은 약 4~5%로, 순차 측정의 6%보다는 작지만
실재한다. 한 대의 기계와 한 개의 문서라는 한계는 그대로다.

해당 지점: `VOCRWindowController.swift:6`의
`activeProcessorCount * 2 / 3` (18코어 → 12).
`* 3 / 4`는 정수 나눗셈이라 18코어에서 13이 된다(18*3=54, 54/4=13). 그래서
13과 14도 교차 측정했다:

| 반복 | 13워커 | 14워커 |
|---|---|---|
| 1 | 39.91s | 42.64s |
| 2 | 46.00s | 45.70s |
| 3 | 46.03s | 46.97s |

**13과 14는 노이즈 안에서 동률이다**(중앙값 46.00 vs 45.70, 13이 3쌍 중 2쌍 승).
따라서 `activeProcessorCount * 2 / 3` → `* 3 / 4` 한 줄 변경이면 12 대비 이득을
그대로 얻는다.
**적용하지 않았다** — 단일 기계·단일 문서 데이터이므로 사용자 판단 사항으로 남긴다.

## 판정 5 — 자식 page-parallelism은 무효가 아니다 (기존 기록 정정)

12워커, 자식 `--page-parallelism 1`:

| 설정 | median wall | 피크 RSS |
|---|---|---|
| pp 기본(8) | 49.53s | 4252.8 MB |
| pp=1 | 54.42s | 3852.6 MB |

pp=1은 **10% 느리고** 메모리는 9% 적다. 기존 프로젝트 기록의 "in-process
page-parallelism은 throughput에 무효"는 단일 프로세스 실험에서 나온 결론이고,
**split 환경에서는 성립하지 않는다.** 워커당 페이지가 적을 때도 pp>1은
렌더와 인식의 겹침으로 약 10%를 벌어준다. 메모리를 줄이려면 쓸 수 있는
트레이드오프 노브지만 기본값으로는 손해다.

## 실제로 좋아진 것

속도가 아니라 **검증 가능성과 안정성**이다.

- 테스트 91개(0.243s, 전부 유닛) → 99개(5.9s). 늘어난 시간은 실제로 프로세스를
  띄운다는 뜻이다. 멀티프로세스 경로 자동 커버리지 0 → 6개:
  성공/병합, **인자 벡터 완전 일치 검사**, `--page-breaks` 전달, PDF 인자,
  워커 실패 전파 + 형제 강제 종료, 일시정지 중 취소.
  인자 벡터 검사는 b8856d6(GUI split에서 `--page-breaks` 누락) 유형을 잡는다.
- CI 없음 → `.github/workflows/ci.yml`.
- 동등성 검증이 손으로 하는 SHA-256 의식 → `scripts/verify-equivalence.sh`.
  TXT `cmp`, `--page-breaks` 변형, PDF **페이지별** 텍스트 비교. 통과 확인.
- 벤치 픽스처 재현 불가 → `scripts/make-bench-fixture.py`(결정적, 래스터 전용,
  텍스트 레이어 없음 단언 내장).
- 종료 안정성: `writeCombinedText` 출력 존재 가드 + 원자적 쓰기,
  SIGTERM 후 2초 유예 → SIGKILL 승격(테스트가 `trap '' TERM` 워커로 실증),
  `readerGroup.wait(timeout:)`, 부모 사망 감시(`APPLE_VISION_OCR_PARENT_WATCH`).

## 검증 범위의 한계 (과장하지 않기 위해 명시)

- **종료가 모든 경우에 제한 시간 내 보장되지는 않는다.** 오류·취소 경로는
  SIGTERM → 2초 → SIGKILL로 제한되지만, 정상 경로의 `readerGroup.wait()`는
  여전히 무제한이고, 오류 경로의 timeout도 `availableData`에서 블록된 리더
  스레드를 깨우지는 못한다.
- **부모 SIGSTOP 중 사망은 여전히 자식을 남긴다.** 감시 스레드도 함께 멈추기
  때문이다. 코드 주석에 남겼다.
- **CI는 파일만 생성됐고 원격 실행 성공은 확인하지 않았다.** 로컬에서 동일한
  두 명령(`swift build -c release`, `swift test`)이 통과하는 것까지가 근거다.
- **동등성은 신·구 버전 간 품질 보존의 증거가 아니다.** 같은 바이너리 안에서
  single과 split이 일치한다는 것만 보장한다.
- 픽스처는 균일 밀도·회전 없음·기존 텍스트 레이어 없음이다. 회전 페이지와
  텍스트 레이어가 있는 입력은 여전히 split 경로에서 독립 검증되지 않았다.

## 남은 것

- 12워커 4.2GB 메모리. 큐로는 못 줄인다. 줄이려면 워커 수를 줄이거나
  프로세스당 모델 적재 비용 자체를 건드려야 한다.
- 텍스트 레이어가 있는 PDF에서 3b의 실이득 측정(현재 픽스처로는 불가).

# 2차 조사 — "CPU/GPU/ANE가 모두 낮다"

사용자 보고에서 출발해 시스템 전체를 계측했다. 결과는 보고와 달랐고,
그 차이가 진짜 병목을 가리켰다.

## 실제 자원 사용 (12워커 실행 중, 3초 간격 샘플링)

- **우리 프로세스 트리 CPU: 1200~1440%** (1800% 중 약 70%). 낮지 않다.
- **GPU Device Utilization: 0~21%, 대부분 13% 미만.** 거의 안 쓴다.
- 우리 밖에서 CPU를 먹는 숨은 데몬 없음 (WindowServer/기타 앱뿐).
- 코어 구성은 `hw.perflevel0.name=Super`(6개) + `hw.perflevel1.name=Performance`(12개)다.
  **효율 코어가 아니다.** (한때 6P+12E로 적었으나 sysctl로 확인해 정정한다.)
  따라서 워커당 페이지 비용이 워커 수에 따라 오르는 것(2.86 → 3.33 → 4.35 → 4.95 →
  6.4 s/page)은 **원인 미확정**으로 남긴다.

## 연산 장치 강제는 효과 없음 (기존 기록 정정)

프로젝트 기록은 "VNRecognizeTextRequest에 compute-units 선택 API가 없다"고
적고 있었으나, **macOS 14+에 `setComputeDevice(_:forComputeStage:)`가 있다**
(`Vision/VNRequest.h:146`). `VNComputeStageMain`에 대해 세 장치가 모두 보고된다:
`MLNeuralEngineComputeDevice`, `MLGPUComputeDevice(Apple M5 Pro)`, `MLCPUComputeDevice`.

한 페이지 3회 최소값:

| 설정 | 시간 |
|---|---|
| 기본(미지정) | 2.745s |
| ANE 강제 | 2.948s |
| GPU 강제 | 2.801s |
| CPU 강제 | 2.824s |

**전부 노이즈 안이다.** 장치를 지정해도 달라지지 않는다. `VNComputeStagePostProcessing`
에 대해서는 지원 장치가 아예 보고되지 않는다. GPU가 노는 것은 맞지만 그쪽으로
일을 보낼 수단이 없다 — 이제 추측이 아니라 측정된 사실이다.

## 진짜 병목: `usesLanguageCorrection`

시간의 대부분은 신경망 인식이 아니라 **CPU에서 도는 언어 모델 후처리**다.
CPU 70% / GPU 10%라는 그림이 정확히 이것이다.

`VisionTextRecognizer.swift:28`에 `true`로 하드코딩되어 있다. 끄면:

| 조건 | 보정 ON | 보정 OFF | 품질 손실 | 속도 |
|---|---|---|---|---|
| 렌더 2.0 / JPEG q1.0 | 0.9911 | 0.9911 | 0.0000 | **3.19x** |
| 렌더 2.0 / q0.4 | 0.9899 | 0.9898 | −0.0001 | 3.05x |
| 렌더 1.5 / q0.5 | 0.9902 | 0.9898 | −0.0004 | 3.14x |
| 렌더 1.25 / q0.5 | 0.9832 | 0.9830 | −0.0002 | 2.94x |

품질은 **정답 텍스트 대비**로 채점했다(픽스처를 직접 생성했으므로 정답을 안다).
유사도가 아니라 실제 정확도다. 깨끗한 입력에서는 5페이지 출력이 문자 단위로
완전히 동일했고(일치 문자 21187/21347로 양쪽 같음), 실제 문서
`Samples/sample.pdf`·`sample_ocr.pdf`에서도 텍스트가 동일하며 3.05~3.32배 빨랐다.

**보정이 실제로 값어치를 하는 지점:** 병리적으로 열화된 입력(520×673, 약 61dpi,
JPEG q0.25)에서는 일치 문자 1673 vs 789로 보정이 정확도를 2배 이상 올린다.
다만 그 구간은 양쪽 다 판독 불가라 실사용 의미는 없다.

## 규모 검증 — 120페이지 엔드투엔드 (5페이지 표본의 과장 정정)

5페이지에서 "출력이 문자 단위로 완전 동일"이라고 적었으나, **표본이 작았다.**
CLI로 120페이지·12워커를 교차 실행한 결과:

| | rep1 | rep2 |
|---|---|---|
| 보정 ON | 43.52s | 45.86s |
| 보정 OFF | **17.50s** | **17.45s** |

**2.5배.** 출력은 동일하지 않다 — 5039줄 중 **41줄(0.81%)이 다르다**(순 12바이트).
(앞서 82줄이라고 적은 것은 `diff | grep '^[<>]'`가 삭제·추가를 이중 집계한 오류다.)
차이는 `lines`→`ines`, `P008`→`PO08` 같은 문자 단위 오류다.

정답 대비 채점:

| | 평균 줄 정확도 | 완전 일치 줄 |
|---|---|---|
| 보정 ON | 0.99403 | 38.06% |
| 보정 OFF | 0.99397 | 37.65% |

**정확도 차이 0.006%(완전 일치 줄 기준 0.41%p)에 시간 2.5배.**
보정이 더 정확한 것은 맞으나, 그 대가가 2.5배다.

이 채점의 한계: `SequenceMatcher.ratio()`는 표준 CER이 아니고, 마커를 인식하지
못한 줄을 평가에서 제외했으며 ON/OFF의 평가 분모가 4798 vs 4794로 다르다
(오류가 심한 줄이 빠지는 편향). 차이의 방향과 크기는 신뢰할 만하나 절대값은
엄밀한 CER이 아니다.

## 결론

이 도구가 실제로 쓰는 렌더 스케일 전 구간에서 언어 보정은 **정확도를 0.006%
올리려고 시간을 2.5배 쓴다.** 지금까지 세션에서 찾은 어떤 레버보다 크다.

구현: 기본값은 바꾸지 않고(보정 유지) CLI `--no-language-correction`,
GUI 체크박스, split 자식 전달로 노출한다. 기본값 전환은 사용자가 자기
문서로 확인한 뒤 결정할 사항이다.

한계: 픽스처는 합성 텍스트 한 종류의 폰트이고, 실제 검증 문서는 2개뿐이며 아주
짧다. 기울어짐·뒷장 비침·다양한 활자가 있는 진짜 스캔본은 검증되지 않았다.

# 3차 — 사용자가 실제로 겪는 경로

앞선 측정은 전부 **오늘 빌드한 CLI**로 했다. 사용자가 실행하는 것과 다르다.

## 원인 1: 설치본이 6월 13일 빌드다

| 경로 | 해시 | 날짜 |
|---|---|---|
| `.build/release/apple-vision-ocr` | `c8d2735a` | 2026-09-09 |
| `~/.local/bin/apple-vision-ocr` | `a1c7bd20` | 2026-06-13 |
| `~/Applications/VOCR.app/.../apple-vision-ocr` | `a1c7bd20` | 2026-06-13 |

Finder 우클릭은 설치본을 실행한다. 이번 라운드의 어떤 변경도 사용자에게
아직 도달하지 않았다. `scripts/install-vocr-quick-action.sh` 재설치가 필요하다.

## 원인 2: TXT+PDF 동시 출력은 단일 프로세스로 폴백한다 (핵심)

`OCRJobController.swift:193`은 TXT와 PDF를 함께 요청하면
"TXT+PDF 동시 출력은 단일 프로세스로 실행합니다"를 찍고 in-process 경로를 탄다.
CLI는 아예 거부한다: `--split-workers cannot be combined with simultaneous text and PDF output`.

실측(20페이지): 단일 프로세스 **59.23s** vs split-12 **9.38s** — **6.3배 손해**.
GUI에서 두 출력을 다 켜면 1~2코어만 돈다. **이것이 사용자가 본 "사용률이 매우
낮다"의 가장 유력한 정체다.**

### 해법이 있고, 검증했다

검색 가능 PDF에는 이미 인식된 텍스트가 들어 있으므로 OCR을 두 번 할 필요가 없다.
split으로 PDF를 만든 뒤 그 텍스트 레이어에서 TXT를 추출하면 된다.

- split-12로 PDF 생성: **10.09s**
- 그 PDF에서 PDFKit으로 추출한 텍스트 vs 직접 생성한 TXT: **85371자로 완전 동일**

**구현 완료 (2026-09-10). 다만 더 나은 방식을 택했다.**

PDF에서 텍스트를 역추출하는 대신, **자식이 한 번 OCR해서 두 출력을 다 쓰게** 했다.
`SearchablePDFPipeline`은 원래 한 번의 인식으로 두 출력을 만들 수 있으므로 자식은
`--output chunk.pdf --txt-output chunk.txt --page-range A-B`를 받고, 부모는 기존
`mergePDFs`와 `writeCombinedText`를 그대로 재사용해 병합한다. TXT가 기존
`TextOutputWriter` 경로로 계속 나오므로 **출력 형식이 전혀 바뀌지 않는다.**

변경: `CLIOptions`의 "복합 출력에 `--split-workers`/`--page-range` 금지" 가드 제거,
`SplitProcessOCRRunner.Output`에 복합 케이스 추가, `CommandRunner` 라우팅,
`OCRJobController`의 XOR 폴백 조건 제거.

실측 (20페이지 밀집 문서):

| 경로 | 시간 |
|---|---|
| 단일 프로세스 (기존) | 58.72s |
| split-12 | **10.89s (5.4배)** |
| split-12 + 언어보정 OFF | **4.70s (12.5배)** |

동등성: TXT **바이트 단위 완전 동일**(130731 bytes), PDF 20쪽 페이지별 텍스트 전부 일치.
`--page-breaks` 조합도 마커 20개가 정상 생성된다. 103 tests 통과.

## 보정을 꺼도 in-process 병렬은 여전히 무효

"직렬화가 보정 경로에 있었을 수 있다"는 가설을 실측으로 기각했다.
20페이지, `--no-language-correction`:

| pp | 시간 |
|---|---|
| 1 | 20.25s |
| 4 | 20.41s |
| 8 | 20.33s |
| 16 | 20.51s |

(같은 조건 보정 ON: pp1 59.23s, pp8 61.57s.) 직렬화는 보정이 아니라 Vision
인식 자체에 있다. 멀티프로세스가 여전히 유일한 병렬 수단이다.
